# 迁场日接驳通知工具

采集本机演练来源（订座段清单见 `requests/example.json`），按行程产出可办通知清单，
并跨演练阶段维护通知台账：哪些旅客该收到「换集合点」、哪些要先人工改签、哪些还缺承运人确认。

## 用法

```bash
npm start                                  # 先启动演练来源（默认 127.0.0.1:3100）
node notify/cli.mjs collect                # 采集四类来源 + 评估 + 对账 + 打印通知清单
node notify/cli.mjs list                   # 查看台账（待办 / 已确认 / 已失效）
node notify/cli.mjs claim   N-0001 --agent K01   # 客服领走
node notify/cli.mjs confirm N-0001 --agent K01   # 客服确认办结
node notify/cli.mjs reset                  # 清空台账
```

可选参数：`--origin`、`--request`、`--store`（默认 `notify/data/store.json`）。
来源切到下一演练阶段（`POST /replay/phase`）后再跑一次 `collect`，
实绩与先前确认不同时会自动失效旧通知、写明原因并给出当前联络口径。

## 判定口径

- **物理航段身份** = `leg` + 始发站 `serviceDay` + 起降角色。营销编号只用于把订座段
  定位到运营记录，不作身份依据；不同航司分别列出的代码共享航段并成同一物理航段，
  同一行程不会收到重复通知。返航重开取 `recurrence` 最大的当次运行。
- **机场确定顺序**：运营记录实绩 / 承运人确认 > 公告 `exception`（官方过渡保留班次）
  > 通用迁场规则（按当地实际或最可靠当前预计时刻与 `cutoff` 比较）。
- **已起飞但缺落地机场确认** → `待核实`，不下发接驳点（公告预计仅作参考写入口径）。
- **承运人已确认新机场但接驳未发布** → `受影响提醒`，不拿原机场班车填空。
- **换集合点**：已确认机场 + 当地乘车窗口覆盖起降时刻（末班含该分钟）才下发。
- **人工改签**：联程间隔 < 最短换乘 + 重新托运附加分钟，或柜台时段不可用 → 先改签；
  后段接驳不具独立可用性暂不下发，同票其他段的独立可用接驳仍保留。

## 通知类别

| 类别 | 含义 |
| --- | --- |
| 换集合点 | 机场与接驳均已确认，可下发集合点与乘车窗口 |
| 人工改签 | 后段赶不上 / 航班取消或返航未重开，先人工改签 |
| 待核实 | 已起飞缺落地机场确认、运营记录或换乘资料缺失 |
| 受影响提醒 | 承运人已确认新机场，但新接驳信息未发布 |

## 台账与溯源

每条通知记录：采用的来源（接口 + 内容摘要 + 采集时刻 + 演练阶段）、时间口径
（实绩/预计/计划、UTC 与当地时刻、切换 cutoff）、经办轨迹（领走 / 确认）。
资料变化使旧口径失效时，旧通知保留在台账中并写明失效原因与接替通知号。

## 结构

- `notify/lib/sources.mjs` — 来源采集
- `notify/lib/assess.mjs` — 纯函数评估（可单测）
- `notify/lib/reconcile.mjs` — 台账对账、领走 / 确认
- `notify/lib/store.mjs` / `report.mjs` / `time.mjs`
- `notify/cli.mjs` — 命令行入口
- `notify/test/` — 以 `scenario.json` 两阶段资料为夹具的单元测试（`npm test`）
